# IAM templates for the orgshift collector

Generated by `orgshift iam-templates` without a configuration: account IDs and the operator principal are placeholders in angle brackets. Run `orgshift iam-templates --config orgshift.yaml --out docs/iam` to fill them in from your configuration.

One role per collector responsibility. Every role is read-only: its actions come from the operation catalog in `internal/collector/operations.go`, where each is classified by what it does (read, read that AWS bills, session), and a test refuses any write and any billable read without an opt-in. Every statement whose Resource is `*` says why it cannot be narrower. The operator who runs orgshift assumes the management-account roles; the org-management role assumes the member and network roles.

Order of work: create the roles, run `orgshift preflight --config orgshift.yaml` to see which calls are available, denied or unknown per domain, grant what is missing, then `orgshift collect`.

| Responsibility | Role | Account | Permissions file |
|---|---|---|---|
| `org-management` | `OrgshiftOrgRead` | The management account (<management-account-id>). | `org-management-permissions.json` |
| `control-tower` | `OrgshiftControlTowerRead` | The management account (<management-account-id>), called in the landing zone's home region. | `control-tower-permissions.json` |
| `identity-center` | `OrgshiftIdentityCenterRead` | The management account (<management-account-id>), called in the instance's region, or the Identity Center delegated administrator account (see below). | `identity-center-permissions.json` |
| `member-inspection` | `OrgshiftMemberRead` | Every member account (deploy it with a StackSet or your account baseline). | none needed in this build |
| `network` | `OrgshiftNetworkRead` | Each account that owns shared networking (<network-account-id>). | `network-permissions.json` |

## org-management: Organizations, account regions and the management account's shares

**Role name:** `OrgshiftOrgRead`

**Where it goes:** The management account (<management-account-id>). Organizations answers these calls only from the management account or a delegated administrator; see the alternative below.

**What it reads:** Reads the organization, the OU tree, every policy type with its attachments, account tags, delegated administrators, trusted access, the enabled regions of every member account and the RAM shares the management account owns; assumes the member inspection and network roles.

**Trust policy** (`org-management-trust.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgshiftOperator",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "<operator-principal-arn>"
        ]
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Permissions policy** (`org-management-permissions.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrganizationsRead",
      "Effect": "Allow",
      "Action": [
        "organizations:DescribeOrganization",
        "organizations:DescribePolicy",
        "organizations:ListAWSServiceAccessForOrganization",
        "organizations:ListAccountsForParent",
        "organizations:ListDelegatedAdministrators",
        "organizations:ListDelegatedServicesForAccount",
        "organizations:ListOrganizationalUnitsForParent",
        "organizations:ListPolicies",
        "organizations:ListRoots",
        "organizations:ListTagsForResource",
        "organizations:ListTargetsForPolicy"
      ],
      "Resource": "*"
    },
    {
      "Sid": "AccountRegionsRead",
      "Effect": "Allow",
      "Action": [
        "account:ListRegions"
      ],
      "Resource": "*"
    },
    {
      "Sid": "OwnResourceSharesRead",
      "Effect": "Allow",
      "Action": [
        "ram:GetResourceShares",
        "ram:ListPrincipals",
        "ram:ListResources"
      ],
      "Resource": "*"
    },
    {
      "Sid": "AssumeCollectorRoles",
      "Effect": "Allow",
      "Action": [
        "sts:AssumeRole"
      ],
      "Resource": [
        "arn:aws:iam::*:role/OrgshiftMemberRead",
        "arn:aws:iam::<network-account-id>:role/OrgshiftNetworkRead"
      ],
      "Condition": {
        "StringEquals": {
          "aws:ResourceOrgID": "${aws:PrincipalOrgID}"
        }
      }
    }
  ]
}
```

**Why each statement is scoped the way it is:**

- `OrganizationsRead` (*): DescribeOrganization, ListRoots, ListPolicies, ListDelegatedAdministrators and ListAWSServiceAccessForOrganization take no resource. The others accept root, OU, account and policy ARNs, but the collector walks the whole tree and every policy, so a resource list would have to name every OU and policy and change whenever one is added. All eleven return existing state and cannot change it.
- `AccountRegionsRead` (*): ListRegions is called for every member account; the action supports the account resource (arn:aws:account::<management-account-id>:account/o-<organization-id>/<member-id>), so replace * with arn:aws:account::<management-account-id>:account/o-*/* if you prefer a pattern. Calling it for other accounts also requires trusted access for account.amazonaws.com in the organization.
- `OwnResourceSharesRead` (*): GetResourceShares with resourceOwner SELF takes no resource and lists only the shares this account owns; ListPrincipals and ListResources accept resource share ARNs, which are only known once GetResourceShares has answered. Nothing here can create, modify or accept a share.
- `AssumeCollectorRoles` (arn:aws:iam::*:role/OrgshiftMemberRead, arn:aws:iam::<network-account-id>:role/OrgshiftNetworkRead): Scoped to the member inspection role name in any account of the same organization (aws:ResourceOrgID must equal the caller's organization) and to the network roles. The role in the target account still has to trust this one.

**Delegated administrator alternative:** Organizations can delegate its read and policy operations to a member account with a resource-based delegation policy attached from the management account (aws organizations put-resource-policy). The example delegation policy below grants the tree and policy reads to OrgshiftOrgRead in a delegated account (<delegated-administrator-account-id>). Three things stay with the management account: ListDelegatedAdministrators, ListDelegatedServicesForAccount and ListAWSServiceAccessForOrganization are not documented as delegable (preflight reports them denied if so, and the collector records delegated_administrators and trusted_access as access_denied); account:ListRegions for other accounts needs the Account Management delegated administrator (account.amazonaws.com); and the management account's own RAM shares are listed only from the management account.

Example delegation policy (`org-management-delegation-policy.json`), attached from the management account with `aws organizations put-resource-policy --content file://org-management-delegation-policy.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgshiftReadFromDelegatedAccount",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<delegated-administrator-account-id>:role/OrgshiftOrgRead"
      },
      "Action": [
        "organizations:DescribeOrganization",
        "organizations:ListRoots",
        "organizations:ListOrganizationalUnitsForParent",
        "organizations:ListAccountsForParent",
        "organizations:ListPolicies",
        "organizations:DescribePolicy",
        "organizations:ListTargetsForPolicy",
        "organizations:ListTagsForResource"
      ],
      "Resource": "*"
    }
  ]
}
```

**Planned for later milestones** (not in the permissions policy; listed so the role's eventual scope is known):

| Action | Kind | Fills | Opt-in | Purpose |
|---|---|---|---|---|
| `cloudtrail:DescribeTrails` | read | `organization_trails` |  | organization trails |
| `cloudtrail:GetTrailStatus` | read | `organization_trails` |  | whether each organization trail is logging |
| `cloudformation:ListStackSets` | read | `stack_sets` |  | service-managed StackSets |
| `cloudformation:DescribeStackSet` | read | `stack_sets` |  | targets and auto-deployment of each StackSet |
| `cloudformation:ListStackInstances` | read | `stack_sets` |  | the accounts and regions each StackSet is deployed to |
| `cloudtrail:StartQuery` | read-billable | `usage.actions` | `billable.cloudtrail_lake (--with-cloudtrail-lake)` | one aggregated CloudTrail Lake query for actions in use |
| `cloudtrail:GetQueryResults` | read-billable | `usage.actions` | `billable.cloudtrail_lake (--with-cloudtrail-lake)` | results of the Lake query |
| `cloudtrail:DescribeQuery` | read-billable | `usage.actions` | `billable.cloudtrail_lake (--with-cloudtrail-lake)` | status and bytes scanned of the Lake query |

**Notes:**

- sts:GetCallerIdentity is called first to check that the credentials belong to account <management-account-id>; it needs no permission.
- The AWS managed policies ReadOnlyAccess and AWSOrganizationsReadOnlyAccess also cover these calls but are far broader.

**Create it:**

```sh
aws iam create-role --role-name OrgshiftOrgRead --assume-role-policy-document file://org-management-trust.json --description "orgshift read-only collector: Organizations, account regions and the management account's shares" --max-session-duration 3600
aws iam put-role-policy --role-name OrgshiftOrgRead --policy-name OrgshiftOrgRead --policy-document file://org-management-permissions.json
```

## control-tower: Control Tower landing zone, baselines and controls

**Role name:** `OrgshiftControlTowerRead`

**Where it goes:** The management account (<management-account-id>), called in the landing zone's home region. AWS Control Tower has no delegated administrator for its APIs.

**What it reads:** Reads the landing zone (version, drift, auto-enrollment, governed regions), the registered OUs and enrolled accounts from the enabled baselines, the controls enabled on each registered OU and their names and behaviours from the Control Catalog.

**Trust policy** (`control-tower-trust.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgshiftOperator",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "<operator-principal-arn>"
        ]
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Permissions policy** (`control-tower-permissions.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ControlTowerRead",
      "Effect": "Allow",
      "Action": [
        "controltower:GetLandingZone",
        "controltower:ListEnabledBaselines",
        "controltower:ListEnabledControls",
        "controltower:ListLandingZones"
      ],
      "Resource": "*"
    },
    {
      "Sid": "ControlCatalogRead",
      "Effect": "Allow",
      "Action": [
        "controlcatalog:GetControl"
      ],
      "Resource": "*"
    }
  ]
}
```

**Why each statement is scoped the way it is:**

- `ControlTowerRead` (*): ListLandingZones, ListEnabledBaselines and ListEnabledControls take no resource. GetLandingZone accepts the landing zone ARN, which is only known after ListLandingZones answers, and an organization has one landing zone. None of the four can enable, disable or reset anything.
- `ControlCatalogRead` (*): GetControl accepts control ARNs (arn:aws:controlcatalog:::control/*), which are discovered from the enabled controls at collection time. The catalog is AWS reference data, identical for every account; the call only names and classifies controls.

**Delegated administrator alternative:** None. The landing zone, baseline and control operations are called from the management account; create this role there. Without it the collector records control_tower and control_tower.enrolled_accounts as access_denied and the Control Tower check reads REVIEW.

**Planned for later milestones** (not in the permissions policy; listed so the role's eventual scope is known):

| Action | Kind | Fills | Opt-in | Purpose |
|---|---|---|---|---|
| `servicecatalog:SearchProvisionedProducts` | read | `control_tower.enrolled_accounts` |  | Account Factory provisioned products, for enrolment provenance |

**Notes:**

- Set control_tower.home_region in the configuration: the APIs answer only there, and an empty answer elsewhere is recorded as an error when trusted access shows Control Tower is in use.

**Create it:**

```sh
aws iam create-role --role-name OrgshiftControlTowerRead --assume-role-policy-document file://control-tower-trust.json --description "orgshift read-only collector: Control Tower landing zone, baselines and controls" --max-session-duration 3600
aws iam put-role-policy --role-name OrgshiftControlTowerRead --policy-name OrgshiftControlTowerRead --policy-document file://control-tower-permissions.json
```

**References:** https://docs.aws.amazon.com/service-authorization/latest/reference/list_awscontroltower.html, https://docs.aws.amazon.com/service-authorization/latest/reference/list_awscontrolcatalog.html, https://docs.aws.amazon.com/controltower/latest/APIReference/Welcome.html

## identity-center: IAM Identity Center instance, permission sets and assignments

**Role name:** `OrgshiftIdentityCenterRead`

**Where it goes:** The management account (<management-account-id>), called in the instance's region, or the Identity Center delegated administrator account (see below).

**What it reads:** Reads the instance and its identity store ID, every permission set with its managed, customer managed and inline policies and boundary, the accounts each is provisioned in, the assignments on those accounts, and the user and group names behind the assignment principals.

**Trust policy** (`identity-center-trust.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgshiftOperator",
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "<operator-principal-arn>"
        ]
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Permissions policy** (`identity-center-permissions.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "IdentityCenterRead",
      "Effect": "Allow",
      "Action": [
        "sso:DescribePermissionSet",
        "sso:GetInlinePolicyForPermissionSet",
        "sso:GetPermissionsBoundaryForPermissionSet",
        "sso:ListAccountAssignments",
        "sso:ListAccountsForProvisionedPermissionSet",
        "sso:ListCustomerManagedPolicyReferencesInPermissionSet",
        "sso:ListInstances",
        "sso:ListManagedPoliciesInPermissionSet",
        "sso:ListPermissionSets"
      ],
      "Resource": "*"
    },
    {
      "Sid": "IdentityStoreNames",
      "Effect": "Allow",
      "Action": [
        "identitystore:DescribeGroup",
        "identitystore:DescribeUser"
      ],
      "Resource": "*"
    }
  ]
}
```

**Why each statement is scoped the way it is:**

- `IdentityCenterRead` (*): ListInstances takes no resource. The eight others are scoped to the instance (arn:aws:sso:::instance/ssoins-*) and its permission sets (arn:aws:sso:::permissionSet/ssoins-*/ps-*); the instance ID is only known after ListInstances answers. Once you know it, replace * with those two patterns. None of the nine can create, provision or assign anything.
- `IdentityStoreNames` (*): DescribeUser and DescribeGroup are scoped to the identity store (arn:aws:identitystore::<account>:identitystore/d-*) and its users and groups (arn:aws:identitystore:::user/* and group/*); the store ID comes from ListInstances. They only turn principal IDs into names; drop this statement to keep assignments by ID.

**Delegated administrator alternative:** Register a member account as the IAM Identity Center delegated administrator (service principal sso.amazonaws.com), create this role there and point identity_center.access in the configuration at it (from: management, assume_role). The delegated administrator cannot alter permission sets provisioned in the management account, and AWS does not document that it can read them; if they are missing or denied the identity_center coverage record says so and the Identity Center check reads REVIEW for moves that touch them.

**Notes:**

- Set identity_center.region in the configuration: the instance APIs answer only there.

**Create it:**

```sh
aws iam create-role --role-name OrgshiftIdentityCenterRead --assume-role-policy-document file://identity-center-trust.json --description "orgshift read-only collector: IAM Identity Center instance, permission sets and assignments" --max-session-duration 3600
aws iam put-role-policy --role-name OrgshiftIdentityCenterRead --policy-name OrgshiftIdentityCenterRead --policy-document file://identity-center-permissions.json
```

**References:** https://docs.aws.amazon.com/service-authorization/latest/reference/list_awsiamidentitycentersuccessortoawssinglesign-on.html, https://docs.aws.amazon.com/service-authorization/latest/reference/list_awsidentitystore.html, https://docs.aws.amazon.com/singlesignon/latest/userguide/delegated-admin.html

## member-inspection: Member account inspection

**Role name:** `OrgshiftMemberRead`

**Where it goes:** Every member account (deploy it with a StackSet or your account baseline). It trusts arn:aws:iam::<management-account-id>:role/OrgshiftOrgRead.

**What it reads:** Reads what only the account itself can see: IAM last-accessed data for actions in use, networking state for path reasoning, the shares the account receives. This build calls nothing in member accounts; preflight assumes the role to prove the trust works, and sts:GetCallerIdentity needs no permission, so no permissions policy is attached yet. The planned operations below are what M4 adds.

**Trust policy** (`member-inspection-trust.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgshiftCollector",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<management-account-id>:role/OrgshiftOrgRead"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Permissions policy:** none in this build. The role only has to exist and trust the collector; `sts:GetCallerIdentity` needs no permission.

**Delegated administrator alternative:** Not applicable: the role lives in each member account. Accounts created by Organizations carry OrganizationAccountAccessRole and Control Tower accounts carry AWSControlTowerExecution, both full administrators; orgshift does not use them so its read-only scope stays explicit and auditable.

**Planned for later milestones** (not in the permissions policy; listed so the role's eventual scope is known):

| `iam:GetServiceLastAccessedDetails` | read | `usage.actions` |  | read the last-accessed report |
| `cloudtrail:LookupEvents` | read | `usage.actions` |  | management events of the last 90 days (free, slow) |

## network: Shares owned by a network account

**Role name:** `OrgshiftNetworkRead`

**Where it goes:** Each account that owns shared networking (<network-account-id>). RAM lists only the caller's own shares, so the transit gateways, subnets, Resolver rules and prefix lists shared from a network account are invisible from the management account. It trusts arn:aws:iam::<management-account-id>:role/OrgshiftOrgRead.

**What it reads:** Lists the resource shares the network account owns, with their principals, resources and the retain-on-leave setting.

**Trust policy** (`network-trust.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OrgshiftCollector",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<management-account-id>:role/OrgshiftOrgRead"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Permissions policy** (`network-permissions.json`):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "OwnResourceSharesRead",
      "Effect": "Allow",
      "Action": [
        "ram:GetResourceShares",
        "ram:ListPrincipals",
        "ram:ListResources"
      ],
      "Resource": "*"
    }
  ]
}
```

**Why each statement is scoped the way it is:**

- `OwnResourceSharesRead` (*): GetResourceShares with resourceOwner SELF takes no resource and lists only the shares this account owns; ListPrincipals and ListResources accept resource share ARNs, which are only known once GetResourceShares has answered. Nothing here can create, modify or accept a share.

**Delegated administrator alternative:** Not applicable: RAM has no organization-wide view of shares owned by other accounts, so each owning account needs its own role (or a profile with equivalent read access, named under network in the configuration).
